Prepare and run
the SME code review demo

The last task in Phase 3. A short, live walkthrough for someone who knows the domain — feedback captured as real GitHub issues, not just notes you might forget. Written for macOS.

00What you are building

By the end of this you will have:

  • A rehearsed 5-minute demo script covering register → create rota → claim slot → cancel
  • A short prep checklist so nothing breaks mid-demo
  • Every piece of feedback logged as a GitHub issue, not just talked about and forgotten
  • Those issues triaged back into Project OS, so they become real tasks with a phase and a priority
What "SME" means here. Subject Matter Expert — anyone who can look at the working app with fresh eyes and domain knowledge you don't have: a mentor, a tutor, a friend who's organised meals for someone in real life, or your Code Institute assessor if that's who you're showing. It doesn't have to be a developer. The point is a second, informed opinion before you're too deep into the next phase to change course cheaply.
This one's overdue. It was due 15/09 and today's the 22nd. That's fine — better to run it properly late than rush it on time. Just don't let it slip further: the whole reason it sits mid-sprint rather than at the end is so you still have a full week to act on what comes out of it.

01Before you book the session

Fifteen minutes of prep now saves the demo from derailing later.

Make sure the app is in a demo-safe state

Terminal 
cd ~/Documents/vscode-projects/cook_book
source .venv/bin/activate
python manage.py collectstatic --noinput
DEBUG=True python manage.py test

All tests passing is your green light. If anything's red, fix it before you book time with anyone — a bug appearing live is a worse first impression than a short delay.

Decide: local or live?

Local (127.0.0.1:8000)Live (Heroku)
Best for Screen-sharing on a call, or sitting next to someone Sending a link for someone to click through themselves
Watch out for Your Wi-Fi/laptop being visible — close anything private first It's the real, deployed version — any bug here is the one that counts

Reset to clean data

Old test rotas with names like "asdf" and "Test Test" undermine the demo. Either clear them out or create fresh ones with realistic names — "The Okafor family", "Jo Bennett recovering from surgery" — so the reviewer is looking at something that reads like the real thing.

Have two accounts ready

You'll switch roles mid-demo, so log out and back in works better than two browser windows for most people. Know both sets of credentials before you start:

  • One Organiser account, with at least one rota already existing (so the reviewer sees the "Rotas running now" list isn't empty on the homepage)
  • One Cook account, not yet claimed anything

02The demo script

Five minutes, four steps. Say what you're doing before you click, not after — it reads as confident rather than narrated-after-the-fact.

Register "This is the sign-up page — you choose Organiser or Cook right here, at registration." Create a new Cook account live, or show the existing one signing in if you'd rather not create test data on camera.

Create a rota Sign in as the Organiser. "This is what it looks like when someone needs a meal rota set up — a few dates, some dietary notes, an address." Fill in a couple of fields, save, land on the rota's detail page.

Claim a slot Switch to the Cook account. "Now someone who wants to help sees the open dates and claims one." Click claim, confirm, show the date now marked as taken.

Cancel "And if their plans change, they can back out themselves — no admin needed." Cancel the same claim, show it's open again.

Why this exact order. It's the same order as your SlotCRUDTests — register, create, claim, cancel — because that's the actual user journey the whole app exists for. If a reviewer only sees one thing, it should be this loop, not the admin panel or the CSS.

03Capture feedback as issues, live

This is the step the task is actually graded on — not the demo itself, but whether the feedback survives it. Have a second window open on your GitHub repo the whole time.

Browser — new tab, kept open throughout 
github.com/sarahjhill/community-cooking-rota/issues/new
Don't wait until afterwards. "I'll remember that" is exactly how good feedback gets lost. The moment the SME says something — even something small, even something you disagree with — open a new issue for it before you move on to the next part of the demo. It takes twenty seconds and means nothing depends on your memory an hour later.

Keep every issue to the same short shape so they're easy to triage afterwards:

Issue title 
[SME] Claiming a slot doesn't say who else is on the rota
Issue body 
Raised during the SME code review demo, 22/09/2026.

What they said: "I'd want to see who else is cooking before I commit to a date,
in case I want to swap with someone I know."

My take: reasonable — rota_detail.html already has the full slot list, so this
is showing existing data differently, not a new feature. Low effort.

Suggested priority: Medium

Label each one sme-feedback so they're easy to find as a group later — type the label name and choose "Create new label" the first time.

No such thing as too small to log. "I like the colour" is worth an issue if it's genuine feedback — you're not obligated to act on everything, but you can't triage what you didn't write down. Deciding something doesn't need doing is a real outcome of triage; forgetting it existed isn't a decision at all.

04After the demo — triage into Project OS

Issues on GitHub are the record. Project OS is where they become work with a phase, a priority, and a due date. Do this within a day of the demo, while the context is still fresh.

  1. Re-open each sme-feedback issue and decide: fix now, fix later, or won't fix (and say why in a comment, then close it)
  2. For anything you're doing, go to Process in Project OS and click + Add your own task under the right phase — usually 4. Notifications or 5. Testing & QA, depending what the feedback was about
  3. Give it the GitHub issue's title, link the issue itself under Linked documents on the new task, and set a realistic priority — not everything the SME says is Critical

05Try it

  • Ran the full test suite and it's green, before booking anyone's time
  • Both demo accounts sign in without trouble, right now, not "should still work"
  • Walked through the four-step script yourself, once, start to finish, before doing it live for someone else
  • GitHub's "New issue" page is open and ready in its own tab before the session starts
  • Every piece of feedback — however small — became its own issue during the session, not a mental note
  • Each issue that needs work has a matching task in Project OS within a day

06Troubleshooting

SymptomLikely causeFix
Something breaks live that passed in tests Usually stale demo data, not a real regression Say so plainly — "that's my test data, not the app" — and carry on; don't debug live on camera
SME feedback contradicts your own plan Perfectly normal — that's what the review is for Log it anyway. Disagreeing with feedback isn't a reason not to record it — decide later, with a clear head
You forgot to log something until after the call ended Happens to everyone the first time Write it down from memory immediately, labelled the same way — late is better than never, but do it now, not "later"
Not sure who to ask to be the SME Overthinking "expert" A Code Institute mentor, tutor, or even a friend who's organised a meal train or rota for someone in real life all count — domain sense matters more than a job title
